## 门禁结论

分步骤模式的现有主链已在隔离作品中从故事核心一路运行到正文采纳和章后演化：

```text
故事核心
  → 主线故事线
  → 卷纲
  → 章纲
  → 场景细纲
  → 正文候选
  → 作者采纳
  → 七域章后候选
  → 作者确认写入
  → 章节记忆与计划—正文对账
```

每一级都以作者已经采纳的上游 Canon 为基线。候选刷新可恢复，作者修改正式内容后旧候选会 stale，
作者确认前不会写入目标 Canon。真实运行还证明了正文、5 个场景细纲、章节摘要、故事线进度和计划对账
在页面刷新后仍能恢复。

本门证明的是当前工程主路径可以运行，不等同于“以后不会再出现 Bug”，也不把一章真实生成外推成百万字
文学质量结论；百万字符的有界检索能力由独立 Phase 4 工程规模门签收。

## 真实整链证据

### 1. 故事核心与故事线

1. 从隔离空项目生成 StoryCore 一句话故事，候选确认后写入正式故事核心。
2. 基于已采纳 StoryCore 生成并采纳主线 StoryArc。
3. StoryArc 调用记录为 1 次模型请求、约 6,493 tokens、52,228ms，界面估算费用约 `$0.001602`。
4. 空项目下“没有 StoryCore 行”现在被视为可冻结的空意图基线；之后新增 StoryCore 才使旧投影 stale，
   不再把合法空态误报为来源丢失。

### 2. 卷纲、章纲与细纲

1. 生成并采纳 1 个卷纲；实际 usage 为 input 4,814 / output 1,505 tokens。
2. 生成并采纳 1 个章纲；实际 usage 为 input 5,525 / output 616 tokens。
3. 在细纲候选生成后手动新增场景，旧候选先因 merge 协议不满足、再因 `chapters` / `detailedOutlines`
   基线变化被明确 stale 阻断；旧候选没有触碰正式细纲。
4. 作者拒绝旧候选并重新生成。第二次候选为 1 次调用、input 5,970 / output 1,203、总计约 10,983
   tokens、12,034ms，界面估算 `$0.001655`。
5. 作者把候选中的删除动作编辑为保留，最终采纳 4 个生成场景和 1 个手工场景，共 5 个场景、估算约
   10,000 字；刷新后场景数量和内容仍在。

### 3. 正文生成与采纳

1. 正文页显示真实上下文预算：基础指令约 9.9K、核心上下文约 11.2K，总计约 21.2K / 566.0K。
2. 作者明确要求只写第一个场景、约 800～1,200 字且不提前写后续场景；模型生成约 1,487 个字符候选。
3. 首次采纳暴露了真实缺陷：模型输出包含空行时，候选按原始文本计算预期 hash，而富文本编辑器写入前
   会过滤空行，导致同一可见候选被误判为“不一致”。
4. 修复后，候选预期 hash 和编辑器写入统一复用 `normalizeProseForEditorV1()`；架构守卫禁止恢复页面内
   第二套规范化函数。重新生成的候选成功采纳，正式章节为 1,431 个非空白字符。
5. 刷新后正文 1,431 字、5 个场景细纲和章节摘要均恢复。

### 4. 正文后的受控演化

1. 正文采纳后先显示建议任务、模型调用/token/费用范围；作者确认前没有隐藏模型调用。
2. 作者确认后生成七域候选：2 条状态、2 条事实、1 条故事年表、1 条故事线进度；物品、关系和伏笔
   没有通过证据门，因此显示为零候选，而不是编造补齐。
3. 6 个所选候选经作者确认写入；Run #372 显示“正文与章后交接均已完成”。
4. 章节记忆正确总结已写的第一个场景；计划—正文对账区分已完成、未完成、实际偏移、新增约束和下一章
   影响，并逐项展示正文证据。
5. “确认并附加实际进展约束”在本次真实数据上等待作者编辑写队列十余秒后完成并持久化。数据没有丢失，
   但原 UI 没有忙碌反馈；现已增加“正在附加/正在更新”、防重复点击和可见错误提示。

## 本门发现并修复的工程缺陷

1. 主 Agent 正文采纳重放没有恢复 Gateway 的 `chapterId` / `characterId` 作用域轴，严格 freshness 会在
   正确候选上产生假 stale；现由候选冻结快照统一派生并校验。
2. 主 Agent prose-copilot 没有把 Gateway 实际输入来源写入严格 Skill input-state evidence；现按真实
   Gateway execution 派生，不再靠测试宽松通过。
3. `<p><br></p>` 等富文本空占位曾被 `content.trim()` 误判为“已经写正文”，从而阻止空章细纲；现在以
   统一正文文本规范化结果判定，并有反例测试和架构守卫。
4. 正文候选 hash 与编辑器空行处理不一致；现统一为一个工具函数和一个机器守卫。
5. 章节对账确认等待写队列时无反馈；现有明确忙碌、禁重入和错误态。
6. 大纲依据面板在只有正式 StoryArc 时可能错误提示“未填写故事主线”；现在直接展示已确认故事线，
   只有 StoryCore 与 StoryArc 都为空才提示依据缺失。

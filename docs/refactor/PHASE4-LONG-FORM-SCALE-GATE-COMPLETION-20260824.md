# Phase 4 完成卡：十万、三十万、百万字符长篇规模门

日期：2026-08-24

任务：`PHASE4-LONG-FORM-SCALE-GATE`

状态：工程规模门通过；允许进入 Phase 5 发布收口

## 结论

分步骤正文主链已经具备“按章持续推进到百万字符”的工程基础。它没有把整本书塞进一次模型请求，而是把
章纲、细纲、故事线阶段、已确认事实、视角角色认知、叙事蓝图、上一章连续性和长期一致性档案分成可寻址
资源；每次只装配当前任务的有界 Context Packet。

本门使用全新的、未送给模型的宿主侧证据义务，在 10 万、30 万和 100 万字符三档分别建立 50、150、500
章的隔离作品。每档都要求下一章正文装配同时满足：

- 回链第一章建立的远距硬事实；
- 回链全书中段埋下的伏笔；
- 保留最近一章原文尾部；
- 保留当前视角角色认知；
- 读取激活叙事蓝图；
- 读取目标章细纲；
- 不读取未来章泄漏标记；
- 不读取其它世界泄漏标记；
- Context Packet 不超过 64K 检索 token；
- 目录检索零模型调用、零额外工具轮次；
- artifact hash、检查结论或度量被篡改后验签失败。

三档全部通过。最终定向联测中的上下文装配耗时分别约为 `0.71s / 1.30s / 5.23s`；数值是本机工程基线，
不是所有设备的性能承诺。

## 本门发现并修复的问题

首轮 10 万与 30 万档通过，但百万档在 180 秒冻结上限内超时。根因不是正文进入 Prompt，而是目录已经选出
资源后，Provider 又按 portable UID 从表头线性扫描每一个待读资源，章节数与读取数叠加后形成近似二次放大。

修复在 Canon Provider 内增加可完全丢弃的内存定位器：

```text
当前 Dexie cache epoch + scope fingerprint + resourceKey
  -> PROJECT_TABLES 表名 + recordId
```

定位器只负责加速。正式读取仍重新加载记录并复核 scope、内容 hash 和 policy hash；任意 StoryForge 写入都会
推进既有全局 cache epoch，旧定位器因此立即失效。没有新增 IndexedDB 表、schema、手写业务表清单、上下文源
或写回旁路。定位器还设有 10 万项内存上限，超过后整体丢弃并允许权威扫描回退；架构检查已冻结其 epoch、
scope 复核和可丢弃属性，防止以后退化为第二身份源。

修复后 30 万档从约 `14.5s` 降到约 `1.5s`，百万档约 `5.2s` 完成。现有直接 Dexie 写入失效、陈旧检索块
回退 Canon、ContextManifest V3 采纳前 freshness 和其它世界隔离反例均继续通过。

## 诚实能力边界

本门证明的是“百万字符规模下，分步骤系统能在有界预算内找到并冻结当前生成所需的远中近证据”，因此支持
百万字级作品按章持续创作的理论工程结论。它不证明：

1. 任意模型都能稳定写出百万字高质量文学作品；
2. 每个作者未结构化表达的隐含伏笔都能被系统自动识别；
3. 已消耗且失败的历史 H4 held-out 已经变成通过；
4. 独立真实作者长期创作研究已经完成；
5. 系统从此没有任何 Bug。

H4 真实 verifier 的历史 sealed held-out 仍维持原始 `FAIL`，不得复用或重跑。本次是新的工程规模协议，
没有借旧样本调参，也没有把检索正确性冒充文学质量。真正的模型质量、作者修改量和百万字成书表现仍需
未来独立作者研究或新的冻结生成评测。
